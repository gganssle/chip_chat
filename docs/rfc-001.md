## Summary

 Cilantro is a single Foundry hosted agent with eleven tools — our container, run by Foundry Agent Service — fronted by a public FastAPI service and backed by two data planes with different clocks. Foundry Agent Service offers three shapes as of the 2026 release, and the choice is load-bearing rather than cosmetic: only a hosted agent can export its own OpenTelemetry spans to a backend other than Application Insights, which is what D6 requires. See D8, and docs/decisions/foundry-agent-shape.md for the full argument. Databricks does the expensive overnight thinking — cleaning the harvested menu corpus, building the medallion, computing personalization marts — and publishes into Snowflake. Snowflake is the governed serving layer the agent queries on every turn. Azure AI Search serves menu knowledge; an Azure Functions ops API serves writes.

 Two design properties carry most of the risk and most of the value. Visitor identity is bound at the database session and is not reachable from the model , which makes cross-visitor isolation structural rather than a matter of prompt discipline. And the vision model describes ingredients while a deterministic matcher resolves SKUs , which makes fabricated menu items impossible rather than merely unlikely. Everything else in this document is in service of those two, or is ordinary plumbing.

## Goals and non-goals

#### Engineering goals

 | Five capability lanes behind one conversational surface, with lane-level failure isolation.

 | Median turn latency under two seconds; p95 under four.

 | Visitor isolation enforced below the model, in the data tier.

 | No SKU in any response that does not exist in the catalogue.

 | Spend bounded by an inline, synchronous check — not by alerting.

 | One instrumentation standard feeding both an infrastructure backend and an agent-evaluation backend.

#### Non-goals

 | High availability, multi-region, or any meaningful scale. One region, one replica set, scale-to-zero between visitors.

 | Real payments or fulfilment integration.

 | PII handling. There is none in the system, by construction, and that is a design constraint to preserve rather than a gap to close.

 | Authentication. Deliberately absent; see D5.

## Data model

 Snowflake holds two populations that must never blur: the real catalogue, harvested and versioned, and the synthetic account data generated against it. Every visitor-scoped table carries demo_id and a row access policy.

 -- Catalogue (real, harvested, versioned) 
menu_items item_id, name, category, description,
 calories, allergens[], source_url, harvested_at
item_prices restaurant_id, item_id, unit_price, unit_delivery_price,
 is_available, source_url, harvested_at
modifiers modifier_id, item_id, name, delta_calories
stores store_id, name, city, region, hours

 Price is a column on a restaurant, not on an item. Chipotle's published prices vary by nearly twenty percent between stores — a Steak Burrito was $11.15 at one restaurant and $13.15 at another on the same afternoon — so the single base_price and delta_price columns this section originally carried would each have had to name one store's number and present it as the price. menu_items and modifiers keep identity and structure, which are the same everywhere; item_prices carries money, keyed by restaurant. A quoted price therefore always has a store and a harvested_at attached to it, which is what §08's citation requirement needs of it. See docs/decisions/menu-pricing.md.

 -- Demo accounts (synthetic, visitor-scoped) 
personas persona_id, label, home_store, seed_points, narrative
demo_visitors demo_id, display_name, persona_id, thread_id,
 home_store_override, stated_preferences, created_at, last_seen
orders order_id, demo_id , store_id, placed_at, status, total
order_items order_id, item_id, qty, modifiers[]
loyalty_ledger entry_id, demo_id , delta, reason, created_at

 -- Gold marts (published nightly from Databricks) 
customer_360 demo_id , order_count, lifetime_spend, last_order_at,
 favourite_store, cadence_days, lapsed_flag
usual_order demo_id , item_id, modifiers[], confidence, derived_at
item_affinity item_id, related_item_id, lift
spend_summary demo_id , period, total, order_count 

 The three fields a visitor may edit — display_name, home_store_override and stated_preferences — are all columns on demo_visitors, and the nightly Databricks jobs do not read that table. Marts are computed from orders, order_items and loyalty_ledger only. That containment is the whole mechanism behind the decision on PRD Q2: it is not that visitors are asked not to invalidate a mart, it is that no editable field is an input to one. A reviewer checks the property by confirming nothing under the medallion pipeline selects from demo_visitors. home_store_override changes where the next order would be priced, not where past orders happened, so customer_360.favourite_store — derived from orders.store_id — remains correct and may legitimately disagree with it; the serving layer says so rather than reconciling silently. See docs/decisions/persona-editing.md.

## Identity and the trust boundary

 This is the section to read if you read only one. The agent is a program that takes untrusted input — visitor text, harvested web documents, uploaded photographs — and produces output that is itself untrusted. Any design where that program is also responsible for asserting whose data to return is one prompt away from a disclosure.

 So it isn't. Identity originates in the app's server-side session store, is applied to the Snowflake connection as a session variable, and is enforced by row access policies on every visitor-scoped table. No tool signature accepts a visitor identifier. That absence is the enforcement mechanism — there is no argument for the model to get wrong, no field for an injected instruction to populate, and no code path where a mistake in the system prompt becomes a data leak.

 IDENTITY PATH — TRUSTED 

 Visitor browser 
 types a name 

 App session store 
 cookie → demo_id, server-side 

 Snowflake 
 row access policy on demo_id 

 session cookie 

 SET demo_id 

 CONTENT PATH — UNTRUSTED 

 Corpus · photo · text 
 all attacker-influenced 

 Foundry agent 
 picks a tool · output untrusted 

 Tools 
 no identity argument exists 

 into the prompt 

 tool call 

 queries — already filtered 

 no path from the model 
 to the bound identity 

 The two vertical edges are the whole argument. On the right, tools query a connection that is already scoped, so the worst a confused model can do is ask the wrong question about the right visitor. On the left, the edge that would let the model choose a visitor does not exist — not blocked at runtime, simply absent from every signature. 

### Connection pooling is where this breaks

 Session variables and pooled connections are a classic combination for cross-tenant bleed. A connection returned to the pool with demo_id still set, then handed to another visitor's request before it's reassigned, defeats every policy above. The pool must set the variable on checkout and clear it on return, and the adversarial suite must include a concurrency test that would actually catch a failure here — sequential tests will pass regardless.

## Tool contracts

 Eleven tools. Note the absent column: none of them takes a visitor identifier, and none of the read tools has side effects.

 | Tool | Arguments | Returns | Writes | Confirm | Backed by 

 | search_menu_knowledge | query | Passages with citations | no | — | AI Search 

 | ask_account_question | question | Answer, generated SQL, rows | no | — | Cortex Analyst 

 | get_points_balance | — | Balance and available rewards | no | — | Snowflake 

 | get_usual_order | — | Order draft with confidence | no | — | Gold mart 

 | get_recommendations | — | Ranked items with rationale | no | — | Gold mart 

 | match_meal_from_photo | blob_ref | Description and candidate draft | no | — | Vision + matcher 

 | propose_order | items[] | Draft id, priced | no | — | App 

 | place_order | draft_id | Receipt | yes | yes | Ops API 

 | cancel_order | order_id | Receipt | yes | yes | Ops API 

 | redeem_points | reward_id | Receipt and new balance | yes | yes | Ops API 

 | update_preferences | prefs | Acknowledgement | yes | yes | Ops API 

 The four write rows are the whole action surface, and what their arguments contain is pinned down in docs/action-surface.md, derived from Chipotle's published ordering menu and rewards terms rather than invented. That document does not add or remove a tool. It does record two things this table reads past: redeeming points mints a Reward with a sixty-day life rather than ordering anything, and cancel_order models an affordance the real product does not offer to customers at all — which is a fact the receipt has to say out loud.

### Confirmation is enforced in the ops API, not the prompt

 Every write tool takes an identifier for something the visitor has already been shown. place_order takes a draft_id the app minted and rendered as a card; the ops API rejects any draft that has not been marked confirmed by a request carrying the visitor's session. An agent that decides to skip the confirmation step produces a rejected call and an eval failure, not an order. The two launch gates in the PRD are both structural properties of this design rather than behaviours we hope to observe.

## Vision pipeline

 Six stages, and the ordering matters. Moderation happens before inference so that nothing unmoderated reaches a model, and the SKU resolution happens after inference so that no model output is trusted as a product identifier.

 | Validate. Size ceiling, MIME allowlist, magic-byte check — not the declared content type, which is attacker-controlled.

 | Normalize. Strip EXIF, re-encode, downscale to the model's working resolution. Blob written with a 24-hour lifecycle rule.

 | Moderate. Content Safety image check. Failure ends the request here with a neutral message.

 | Describe. Vision model returns structured JSON only — slots and confidences, no free text, no product names.

 | Resolve. Deterministic matcher maps each slot to catalogue rows through a constrained vocabulary. Any required slot below threshold escalates to a clarifying question instead of a guess.

 | Propose. Resolved items become a priced draft, rendered as an editable confirmation card.

 // Stage 4 output schema — the model may return nothing else 
{
 "is_chipotle_style": boolean,
 "vessel": { "value": "bowl|burrito|tacos|salad|quesadilla", "confidence": 0-1 },
 "protein": { "value": <enum from catalogue>, "confidence": 0-1 },
 "rice": { "value": <enum>, "confidence": 0-1 },
 "beans": { "value": <enum>, "confidence": 0-1 },
 "salsas": [ { "value": <enum>, "confidence": 0-1 } ],
 "toppings": [ { "value": <enum>, "confidence": 0-1 } ],
 "meals_visible": integer,
 "notes": string // shown to the visitor, never parsed 
} 

 Every enum is generated from the live catalogue at build time, so the model's vocabulary cannot drift from what is orderable. notes is the only free-text field and is display-only — nothing downstream reads it.

 meals_visible gates the pipeline rather than shaping the draft. At two or more, stage 5 does not run: the schema returns one slot set, so on a frame with several meals those slots describe the photograph rather than any one meal, and resolving them would produce a draft composed entirely of real catalogue items that nobody in the picture is eating. V0 says how many meals it saw and asks which one — it does not pick. Full multi-order support is most of group ordering and stays in V1. See docs/decisions/multi-meal-photos.md.

## Retrieval

 | Chunking follows structure, not length. One menu item is one chunk, carrying its nutrition and allergen fields as metadata. Policy and FAQ documents chunk by section. Fixed-window chunking splits nutrition tables across boundaries and produces exactly the confident wrong answers that allergen questions cannot tolerate.

 | Hybrid retrieval with semantic reranking. Keyword recall matters here more than usual, because item names are proper nouns that embeddings handle poorly.

 | Citations are part of the payload, not reconstructed afterwards. Each chunk carries source_url and harvested_at , and both survive into the response.

 | Citations survive as identifiers, not as prose. Each retrieved passage carries an id, and the response envelope carries a citations array referencing ids the retriever.search span actually returned on that turn. The renderer drops any id that was not retrieved. A model cannot mint a source for the same structural reason D3 means it cannot mint a menu item, and citation presence becomes a deterministic check rather than a second model's opinion. See D9.

 | The index is rebuilt, never patched. The weekly re-harvest produces a new index alias-swapped into place, so a partial harvest can never leave the corpus half-updated.

## Observability

 One instrumentation, two backends: App Insights answers whether the service is healthy, Arize answers whether the agent is behaving. Both consume OpenTelemetry spans carrying OpenInference semantic conventions. Span names are a schema, not a debugging convenience — evaluations and dashboards attach to them, so they are fixed here rather than chosen ad hoc at each call site.

 chat.turn root span — one per visitor message 
├─ guard.budget_check synchronous; may terminate the turn 
├─ guard.content_safety
├─ agent.step one per model round trip 
│ ├─ llm.completion tokens, model, finish reason 
│ └─ tool.<tool_name> one per call, arguments recorded 
│ ├─ retriever.search documents + scores 
│ ├─ db.cortex_analyst generated SQL + row count 
│ ├─ vision.describe image ref + structured output 
│ ├─ matcher.resolve slot confidences + resolved SKUs 
│ └─ ops.<action> draft id + confirmation state 
└─ render.response 

 Phoenix self-hosted during development; the exporter repoints at Arize AX for the public phase, where online evals against real traffic are what justify the cost. Because both speak OpenInference, that is a configuration change — but the unit of configuration differs by tier, and pretending otherwise sets #78 an acceptance criterion it cannot meet. The FastAPI tier's exporter is an environment variable and a restart. The agent's exporter environment variables are immutable per agent version, so repointing the agent means cutting a new agent version whose only diff is OTEL_EXPORTER_OTLP_ENDPOINT, _PROTOCOL, _HEADERS and the connection holding the credentials. No instrumentation code changes either way, which is the claim actually worth proving.

 This fan-out is only available because D8 chose a hosted agent. A prompt agent's tracing goes to Application Insights and stays there — the app's spans would still reach Arize, but agent.step, llm.completion and the per-tool spans would not, and those are the ones trajectory and tool-selection evals score.

 Two consequences of hosting the agent in a container. Its resource attribute service.name is forced to the agent's name and OTEL_SERVICE_NAME is ignored, so one turn's trace carries two service names: the app emits chat.turn, the guards and render.response, the agent emits everything between. W3C trace context must therefore propagate across the app-to-agent boundary or the trace splits in half, and anything filtering on service.name must expect both values. And APPLICATIONINSIGHTS_CONNECTION_STRING is platform-injected on a hosted agent and cannot be overridden — App Insights export is not opt-out per agent, only disabled project-wide. The design wants both backends, so this costs nothing here.

## Failure modes

 The governing principle: a lane may fail, the conversation may not. Cilantro should always be able to say what it cannot currently do and remain useful for everything else.

 | Failure | Behaviour | Blast radius 

 | AI Search unavailable | Knowledge lane declines and says why; other lanes unaffected | Knowledge only 

 | Snowflake unavailable | Account, personalization and action lanes decline; menu questions still work | Three lanes 

 | Cortex Analyst timeout or low confidence | Return “I can't answer that reliably” — never a fallback hand-written query | One question 

 | Vision model unavailable | Ask the visitor to describe the meal in words; the rest of the order flow is unchanged | Vision only 

 | Ops API unavailable | Confirmation card renders but reports that ordering is temporarily unavailable; nothing is half-written | Writes only 

 | Databricks job failed | Serve stale gold marts with their derived_at timestamp; alert; do not silently serve stale data as fresh | Personalization freshness 

 | Daily budget exhausted | Friendly stop state on entry and mid-conversation; no model calls attempted | Everything, gracefully

## Spend control

 The check is inline, synchronous, and sits in front of every model call — a counter in the session store, evaluated before the agent is invoked, backed by a global daily ceiling. Arize reports what was spent; only this prevents it. Those are different jobs and conflating them is how a public demo becomes an invoice.

 | Per-request: refuse if the global daily ceiling is reached.

 | Per-session: cap turns and total tokens, so one visitor cannot consume the day.

 | Per-source-address: rate limit, since sessions are free to mint.

 | Circuit breaker: a manual kill switch that flips the whole app to the stop state, reachable without a deploy.

## Decisions

 D1

### Single agent with tools, not a multi-agent system

 Options
 Single agent with tools · router plus specialist agents · hierarchical planner

 Rationale
 A turn budget of two seconds does not accommodate extra model round trips, a public endpoint's token budget does not accommodate the multiplier, and a single prompt with a single trace is dramatically easier to debug. Most turns need exactly one tool; the work does not decompose.

 Note
 Cortex Analyst is itself a reasoning system, so this is already a two-model design regardless of the label.

 Revisit
 When the write path becomes a separate agent holding the only credentials that can call the ops API — a security boundary rather than decomposition for its own sake.

 D2

### Snowflake serves, Databricks computes

 Options
 Everything in Snowflake · everything in Databricks · split by clock

 Rationale
 Per-turn queries need a governed low-latency store with row-level policies; medallion ETL, chunking and model training need a lakehouse. Splitting on the clock — nightly versus per-turn — puts each workload where it belongs and keeps expensive computation off the conversational path.

 Revisit
 If gold marts start needing sub-hour freshness, which would argue for streaming rather than for collapsing the split.

 D3

### Describe then match, rather than direct SKU prediction

 Options
 Model returns SKUs · model returns free text parsed downstream · model returns constrained slots resolved deterministically

 Rationale
 Asked for product identifiers, a model will confidently produce ones that have never existed. Constraining it to an ingredient vocabulary generated from the live catalogue makes fabrication structurally impossible rather than statistically rare, and moves the failure into a slot confidence we can threshold on.

 Revisit
 Not expected to change. This is the load-bearing decision of the vision lane.

 D4

### Identity bound at the database session, absent from tool signatures

 Options
 Identity as a tool argument · identity injected into arguments by middleware · identity bound at the connection with no argument at all

 Rationale
 Middleware injection still leaves a field in the schema, which means a code path where the model's value could be used and a reviewer has to verify it never is. Removing the parameter entirely removes the class of bug. Enforcement lives in row access policies, which apply regardless of what SQL Cortex Analyst generates.

 Risk
 Connection pooling — see the warning above.

 D5

### Public with no authentication

 Options
 Open · invite codes · federated login

 Rationale
 The product goal is that a link is enough. All data is synthetic, so there is nothing to protect from disclosure; the actual exposure is cost, which is bounded in the application rather than at the door. Isolation between visitors is still enforced, because a demo that leaks between sessions is broken regardless of whether the data is real.

 Revisit
 If abuse exceeds what rate limiting handles, invite codes are the smallest next step.

 D6

### OpenInference over OTel, dual export, Phoenix then Arize AX

 Options
 App Insights alone · Arize alone · one instrumentation, two exporters

 Rationale
 The two tools answer different questions and neither substitutes for the other. Instrumenting once on an open standard means the agent-observability vendor is a configuration value, which is worth demonstrating deliberately.

 D7

### Real menu data, synthetic accounts

 Options
 Everything synthetic · everything harvested · real catalogue with generated accounts

 Rationale
 A synthetic menu makes the knowledge lane meaningless and the action surface arbitrary — the set of things a customer can do should come from the real ordering flow. Synthetic accounts are non-negotiable in the other direction. Keeping the boundary explicit in the schema keeps it explicit in conversation.

 D8

### Hosted agent on a basic-setup project, not a prompt agent

 Options
 Prompt agent, declarative and Foundry-hosted · hosted agent, our container run by Foundry · Responses API with no agent resource at all

 Rationale
 Only a hosted agent reads OTEL_EXPORTER_OTLP_ENDPOINT and will fan out to an arbitrary OTLP endpoint alongside Application Insights. A prompt agent's tracing lands in App Insights and stays there, which does not merely weaken D6 — it removes exactly the spans the second backend exists to consume. The Responses API would give us the whole telemetry path but reopens the custom-orchestrator rejection in §14, whose rationale has not changed. A hosted agent pays the smallest part of that price, keeping the agent resource, thread storage, agent versioning and tool registration, and gives the whole of the D6 benefit.

 Setup
 Basic setup, so threads live in Microsoft-managed storage. Standard setup would keep them in our subscription at the cost of Blob plus AI Search plus Cosmos DB — roughly ninety-seven dollars a month once the collision with the single free AI Search service is priced honestly, against a hundred-and-fifty-dollar budget whose expected steady state is thirty to sixty. It buys data residency over synthetic personas, which is a property this system cannot use.

 Cost
 We ship a container, and the exporter switch in Phase 9 becomes a new agent version rather than an edited setting. Both are real; neither is close to the value of D6.

 Revisit
 If the container build genuinely blocks the Phase 7 demo, a prompt agent is the fallback — but taking it means striking D6 and #78 in the same commit rather than discovering in Phase 9 that the second backend has nothing to show. Full argument in docs/decisions/foundry-agent-shape.md.

 D9

### Citations are a field on the response envelope, rendered inline by default

 Options
 Model writes the source note as text · citations returned on demand behind an interaction · structured citation ids on the envelope, drawn inline by the renderer

 Rationale
 K2 makes a citation mandatory on every food or policy claim and the target for uncited claims is zero, so the check has to be a rule rather than a judgement. A source note the model types is a string a language model produced, which can name a page the retrieval never returned; checking it means asking a second model whether the first one told the truth. Ids that must match the retriever.search span make fabrication impossible instead of unlikely, and reduce the presence check to a comparison. Presentation follows from the same metric: on-demand citations would leave the headline groundedness number scoring a field the visitor never opens, which measures a data structure and reports it as trust. Inline costs one dimmed trailing line per answer, deduplicated by source — PRD Flow 2 was already written this way.

 Allergens
 Stricter, because there the citation is doing safety work: the source renders adjacent to the claim and harvested_at is visible without interaction, since published allergen data goes stale and the corpus is re-harvested weekly.

 Revisit
 If the trailing line hurts readability on a phone, shrink presence to an expanding icon — not to an interaction. A visitor must be able to see, without acting, that the answer came from somewhere. Full argument in docs/decisions/citation-presentation.md.

## Open questions

 Q1
 
 Iceberg tables or the Snowflake connector for the nightly publish? 
 The connector is the shorter path. Iceberg in ADLS read by both engines is the more current pattern and avoids a copy, at the cost of more setup and more that can go wrong on a deadline.

 Q2 — mostly resolved by D8
 
 Does Foundry's thread storage suffice for conversation state? 
 The split is settled: the Foundry thread owns message history, and the app owns everything with a security or cost role — order drafts, confirmation state, budget counters, persona assignment, and the thread_id itself, which is a column on demo_visitors because the decision on PRD Q1 made visitor state outlive the visit. What remains is one empirical number that belongs to Phase 0: how long Microsoft-managed thread storage retains a thread, and whether it can be fetched by id after an arbitrary gap between visits. If it cannot, message history moves into the app store that already exists and nothing else in the split changes. See docs/decisions/foundry-agent-shape.md.

 Q3
 
 Is the semantic reranker available on the AI Search free tier at usable quota? 
 Retrieval quality assumes it. If not, the choice is paying for Basic or redesigning chunking to lean harder on hybrid scoring — worth resolving in Phase 0 rather than Phase 5.

 Q4
 
 How is the nightly demo reset scoped if visitor state persists across visits? 
 Depends on PRD Q1. Persisting sessions and resetting nightly are in direct tension, and the resolution likely involves ageing sessions out rather than truncating tables.

## Alternatives considered and rejected

 | Snowflake Cortex Search instead of Azure AI Search. Would consolidate the stack and remove a service. Rejected because exercising Azure's retrieval stack is an explicit objective — though running both over the same corpus is a cheap and genuinely informative comparison later.

 | A custom orchestrator instead of Foundry Agent Service. More control and more portable. Rejected for the same reason inverted: the managed agent runtime is the thing worth learning here, and hand-rolling the loop teaches agent internals at the cost of the platform.

 | Postgres instead of Snowflake. Cheaper and quite sufficient for this data volume. Rejected because Cortex Analyst and Snowflake's governance model are objectives, not incidental choices.

 | Fine-tuning a model on menu data. Rejected outright. It would trade a citable, updatable corpus for weights that go stale the moment the menu changes and cannot cite anything — the opposite of what the allergen requirements need.

 Requirement identifiers referenced throughout come from the Cilantro PRD. Rollout follows the twelve-phase build plan in the system design document. Service names and tiers across Azure, Snowflake, Databricks and Arize move quickly — verify current ones before implementing against them.
